    Install and sync (brainrc)¶

    brainrc is one Git repo of AI coding-assistant configuration (skills, agents, slash commands, rules, hooks, and MCP servers), written once and synced into Claude Code, Codex CLI, OpenCode, Antigravity CLI, and Cursor by brainrc. Skills reach every harness. Rules, commands, and agents reach only some so far. Guard hooks run in Claude Code, OpenCode, and Cursor (deny only in the last two), and MCP servers sync to Claude Code, Codex, and OpenCode. Details per harness: harness support.

    To use brainrc without editing it, install without a clone. Clone it when you want to change the config itself.

    Install with a clone¶

    git clone <this-repo> ~/brainrc
cd ~/brainrc
python3 scripts/brainrc.py init     # first run: pick harnesses, bring in your CLAUDE.md / AGENTS.md
python3 scripts/brainrc.py status   # dry run: shows what would be linked
python3 scripts/brainrc.py apply    # render rules + create symlinks

    init asks which installed harnesses to manage and writes the answer to harnesses.local.toml. If you already have an instructions file of your own (~/.claude/CLAUDE.md, ~/.codex/AGENTS.md, ...), apply would report it as a CONFLICT, so init copies its text into rules/adopted-<harness>.local.md and moves the original aside as <file>.bak-brainrc-<time>. Adopted text is a local rule, so every harness loads it.

    Run from a project folder, init also finds its CLAUDE.md, AGENTS.md, Cursor rules and Copilot instructions and offers to import them into a pack named imported (brainrc import, packs), which every session then loads; it answers no unless you say yes, or pass --import. It skips your home folder, a brainrc checkout and links to what brainrc renders, and it writes and checks that pack before anything else, so a pack that fails leaves the rest unwritten. Then, when brainrc.local.toml sets no profile yet, it asks for a starter profile, which it writes there (below):

    Starter Profile Leaves out
    minimal minimal: rules only everything but rules
    app (the default) recommended: plus skills, agents, commands and hooks MCP servers, and Gatework's Terraform, AWS, Kubernetes and GitOps skills
    infra full: everything nothing

    Before it writes anything, init shows how many files it will create, change and move aside, how many hooks the next apply installs, and about how many tokens of rules and descriptions every session will load, then asks to go on. --yes takes the defaults without asking (no import, no starter), --harness claude,codex names the harnesses, --starter app or --profile recommended picks the profile, --no-adopt leaves your files where they are, and --dry-run writes nothing. init never runs apply.

    --help lists the commands, and <command> --help shows one command's options. status and apply take --only <harness> (repeat it, or --only claude,codex) to touch only those harnesses and leave the others exactly as they are.

    apply only touches harnesses that are installed, so a machine with just Claude Code gets only ~/.claude changes. A harness counts as installed when its config directory exists (~/.claude, ~/.codex, ~/.config/opencode, ~/.gemini/config, ~/.cursor). The others are named in the output and skipped; enabled = true for one in harnesses.local.toml manages it anyway. apply records what it manages in $BRAINRC_HOME/harnesses.json.

    Each harness's own variable moves its paths: $CLAUDE_CONFIG_DIR for Claude Code (including its .claude.json), $CODEX_HOME for Codex, and $XDG_CONFIG_HOME/opencode for OpenCode. status, apply, doctor and uninstall read the variable when it holds an absolute path and use the default above when it is unset, empty or relative, so run them with the same environment as the harness. If the variable changes between applies, apply and status warn that brainrc's links stay in the old dir, and doctor warns while they are there. uninstall also cleans each harness's default dir, so it removes them unless the old dir was another value of the variable.

    Skills, agents, commands, and hooks are symlinked from each harness back into this repo, so git pull updates them in every harness at once. To stay on a release instead of main, check out its tag (git checkout v<X.Y.Z>, from Releases) and re-run apply. Rules are different: they are rendered into ~/.config/brainrc/instructions.md ($BRAINRC_HOME to change it; $XDG_CONFIG_HOME/brainrc when that is set), so re-run apply after any change to rules/ (edits included), and after you add or remove skills, agents, or commands. For Claude Code, apply also merges the guard hooks into ~/.claude/settings.json (your other hooks are kept; a backup is written first, and the last 5 backups are kept).

    Install without a clone¶

    brainrc also installs as a command from PyPI, with core's rules and hooks bundled (apply fetches Gatework, the default pack). uv fetches a Python 3.11+ if the machine has none:

    uvx brainrc status          # try it without installing: a dry run that writes nothing
uv tool install brainrc     # or: pipx install brainrc
brainrc init
brainrc status
brainrc apply

    With Homebrew, brew install brainrc/tap/brainrc installs the latest release from the brainrc/homebrew-tap tap; brew upgrade brainrc moves it on.

    From Node, npx github:brainrc/brainrc status runs brainrc at the version in the repo's VERSION through uvx, so it needs uv but no Python; without uv it says how to get it. brainrc is not on npm: npx installs the repo itself. Keep the github:: npx brainrc would run whatever someone else publishes to npm under that name. npx may reuse a copy it fetched before, so pin a release that ships the shim with npx github:brainrc/brainrc#v<X.Y.Z>. Like uvx, it suits status and other one-off runs; install the command for apply.

    CI times each of these routes from scratch to the first brainrc status on Linux and macOS, and fails one that takes over 60 seconds (scripts/check_install_time.py, workflow install-time). Homebrew, which installs Python first and whose time swings with the runner, warns over 90 seconds and fails over 180, or when its install breaks.

    Pin a release with uv tool install brainrc==<X.Y.Z> (pipx install brainrc==<X.Y.Z>, uvx brainrc@<X.Y.Z>). Run apply from the installed command, not uvx: links point into the package, and uvx runs it from a cache that uv may clear. If brainrc isn't found after the install, run uv tool update-shell (or pipx ensurepath) and open a new shell. Releases from before PyPI publishing, and commits between releases, install from git: uv tool install git+https://github.com/brainrc/brainrc@v<X.Y.Z> (0.4.0 or later installs as brainrc).

    Already have the old ai-config package installed? Run uv tool uninstall ai-config (or pipx uninstall ai-config): its aicfg command is outdated and works on the old settings home. The aicfg command was removed in 0.5.0: use brainrc.

    Links then point into the installed package, so uv tool upgrade brainrc (or pipx upgrade brainrc) updates every harness. Guard hooks are the exception: apply copies them to $BRAINRC_HOME/hooks/core/ and links there, because the package path changes when an upgrade moves the tool to a new Python. Run brainrc apply after upgrading to refresh the copy. After an upgrade to a new Python, the other links (skills, agents) point at the old path and apply reports them as CONFLICT; brainrc apply --repair relinks them (it does the same after you move a checkout). Homebrew keeps each version under its own path, so after brew upgrade brainrc run brainrc apply --repair. Local files go in ~/.config/brainrc/ ($BRAINRC_HOME): harnesses.local.toml, packs.local.toml, and rules/*.local.md. Packs are local directories or git URLs that brainrc fetches (packs).

    Upgrading from the legacy ~/.config/ai-config/ (or $AICFG_HOME)? 0.5.0 no longer reads them, and init, status, apply and update refuse (writing nothing) until you migrate. Run brainrc migrate --dry-run to see the move, then brainrc migrate: it moves the directory and re-runs apply. With the old AICFG_HOME set, set BRAINRC_HOME to the new location first.

    plugin needs a checkout. Contributors use the clone above.

    brainrc never overwrites a file it doesn't manage. Pre-existing files show up as CONFLICT for you to move into the repo or delete (init does that for instruction files).

    Something missing in a harness? python3 scripts/brainrc.py doctor checks the install without changing anything: stale rules, missing or broken links (after moving the repo, say), broken packs, and unmerged hooks. Each problem comes with its fix. apply --repair relinks the links a moved checkout left broken, and brainrc uninstall takes out everything apply put in (--dry-run first to see it); troubleshooting.md has the details and covers the rest.

    Plugins (no clone)¶

    There are two plugins: brainrc (this repo) carries core's guard hooks and rules, and gatework (brainrc/gatework) carries the skills (including /brainrc-work) and the agents. Install both for what brainrc installs, minus the rules where a harness's plugins can't load them.

    Claude Code¶

    /plugin marketplace add brainrc/brainrc
/plugin install brainrc@brainrc
/plugin marketplace add brainrc/gatework
/plugin install gatework@gatework
    Piece Plugins brainrc
    Skills, agents gatework, named gatework:<name> (/gatework:brainrc-work) yes
    Claude guard hooks brainrc yes
    Rules (rules/) no: plugins can't load instructions into every session yes
    Packs, other harnesses (Codex, OpenCode, Antigravity, Cursor) no yes

    Use one path, not both: together they load every skill and hook twice. For rules with the plugins, copy rules/*.md into your own ~/.claude/CLAUDE.md.

    Codex¶

    codex plugin marketplace add brainrc/brainrc
codex plugin add brainrc@brainrc
codex plugin marketplace add brainrc/gatework
codex plugin add gatework@gatework

    Codex gets Gatework's skills (brainrc-work, brainrc-review, brainrc-gatework-*, and the rest) and the agent files spec-agent reads. Rules don't come with a Codex plugin: run brainrc, or copy rules/*.md into ~/.codex/AGENTS.md. Whether Codex runs the brainrc plugin's guard hooks is not yet verified (harness packages).

    Antigravity CLI¶

    Antigravity CLI (agy) installs each repo as a plugin from its root plugin.json:

    agy plugin install https://github.com/brainrc/brainrc
agy plugin install https://github.com/brainrc/gatework

    The first gets the rules: each rules/*.md carries trigger: always_on, which Antigravity needs to load it. The second gets the skills from Gatework's root skills/. Antigravity has no manifest path for agents, so the role files reach it only as files the brainrc-gatework skill reads. Guard hooks aren't included yet, so use agy's own permission settings. This install was built from Antigravity's public docs and issues and hasn't been run end to end (harness packages).

    Cursor¶

    Cursor loads a checkout as a local plugin from .cursor-plugin/:

    ln -s ~/src/brainrc ~/.cursor/plugins/local/brainrc
ln -s ~/src/gatework ~/.cursor/plugins/local/gatework

    The first gets the rules (each carries alwaysApply: true) and the guard hooks for shell commands and file reads, which deny instead of asking; the second gets the skills and the agents. Use the plugins or brainrc's Cursor links, not both: brainrc links the same skills and hooks (Cursor has no user rules file, so rules come only with the plugin). Built from Cursor's official plugin repo and not yet run in a real Cursor (harness packages).

    Moving from ai-config¶

    The plugin was renamed from the old ai-config to brainrc, and its skills from the old ai-config:<name> to brainrc:<name>. Remove the old one first, or every skill and hook loads twice:

    • Claude Code: /plugin uninstall ai-config@ai-config, then /plugin marketplace remove ai-config.
    • Codex: uninstall ai-config@ai-config and remove its marketplace, per Codex's docs.
    • Cursor: delete the old link ~/.cursor/plugins/local/ai-config.

    Then install brainrc@brainrc as above. doctor warns until the old plugin is gone.

    Platforms¶

    macOS and Linux. Everything installs by symlink, and spec-agent reads its role files through Gatework's skills/brainrc-gatework/roles symlink, so checkouts need symlinks too. On Windows, use WSL, or turn on Developer Mode and run git config --global core.symlinks true before cloning. validate and doctor report a checkout without symlinks, with the fix.

    Per-machine customization (never committed)¶

    File Purpose
    harnesses.local.toml Disable a harness ([cursor] / enabled = false), manage one that isn't detected (enabled = true), or change paths
    packs.local.toml Layer extra repos on top: skills, agents, rules, hooks, spec-agent extensions (packs.md); [gatework] enabled = false drops the default pack
    brainrc.local.toml What this machine installs: profile and exclude (below)
    rules/*.local.md Private rules appended after the shared ones

    brainrc.local.toml picks a profile (brainrc init --profile <name> writes it) and drops items by path:

    profile = "recommended"   # minimal: rules only; recommended: plus skills, agents, commands
                          # and hooks; full (the default): plus MCP servers
exclude = ["skills/brainrc-aws", "gatework:agents/brainrc-infra-*"]   # fnmatch, per source

    A pattern matches an item's path in its source (skills/brainrc-aws), or that path after the pack's name (gatework:skills/brainrc-aws). apply prunes what a profile or pattern drops; validate still checks everything.

    Content that must never live in this repo (an employer's facts and skills, for example) goes in a pack: a separate repo with the same layout. See packs.md. python3 scripts/brainrc.py tokens shows what each skill, agent, and rule costs in context.

    Layout¶

    rules/          Global instructions, as ordered markdown fragments (00-core.md, 10-git.md, ...).
                Concatenated into CLAUDE.md / AGENTS.md.
commands/       Optional, for packs: slash commands. Gatework's (/brainrc-work, /brainrc-review, /brainrc-gatework-*) are skills.
mcp/            Canonical MCP server registry. Env var names only, never secret values.
overrides/      Harness-specific config (Claude guard hooks + settings fragment).
harnesses.toml  Where each harness reads each content type.
packs.toml      The default pack, Gatework (brainrc/gatework, fetched by `apply`); extra source
                repos ("packs") go in packs.local.toml.
VERSION         Core version that packs pin with `requires_core`; changes in CHANGELOG.md.
changelog.d/    One fragment per unreleased change; folded into CHANGELOG.md on release.
brainrc/        The brainrc package: sync, validate, doctor, plugin, tokens (Python 3.11+, stdlib only).
scripts/        brainrc.py (runs the package), evals.py, release.py.
docs/           spec-agent, guardrails, efficiency, formats, troubleshooting, harness packages, roadmap.
tests/          stdlib unittest for brainrc and hooks.
examples/       Sandbox project + tickets for trying spec-agent.
dist/           Generated output (gitignored).
